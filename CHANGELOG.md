# Changelog

## Unreleased — 2026-10-24

- Version `bottle.json`: records now carry `schemaVersion` (`Bottle.currentSchemaVersion` = 1, written by every save). Records without it are legacy version 0 and migrate explicitly in `Bottle.init(from:)` with the defaults they always had (Standard graphics, MSync on, display adopted from the prefix, default compatibility switches, no dependencies; a program's launch options, play history and favorite flag, omitted while empty in every version, mean none, zero and not a favorite); reading never rewrites them, the next metadata write (including a play-history or favorite update) stores version 1. A record with a newer version is refused with the new `MagicWineError.newerVersion` kind and left byte-for-byte unchanged (listing, loading, metadata transitions and `save`), so an older build never silently drops fields a newer one wrote; malformed versions are invalid metadata. Its suggestion is to use the newer MagicWine (no recovery action), and the dashboard's failure card is titled "Saved by a Newer MagicWine" (`PresentedError.title`). `BottleStore` now decodes `bottle.json` once per load instead of up to three times (listing, ownership validation, load), before graphics recovery, which never rewrites it. Verified by new tests (current round-trip with every field including play time, last launch and favorite, a legacy record with a legacy program and each field missing on its own, unchanged bytes on read and version 1 after the next write, play history recorded on a migrated record, newer-version refusal across store operations, malformed versions), every existing decoding test unchanged, and the full suite (305 tests).
- Describe the managed Metal Wine runtimes once: the new `ManagedRuntimeLineage` derives the driver family, current revision (`7`) and historical revisions (`1`–`6`) from `WineMetalBuildPins.componentID` and the archive pins, names their `Runtimes/` directories (`RuntimeInstallation.destination`) and classifies an executable by its canonical location (`isManagedMetal`, `isCurrent`, `isUpgradable`). `WineRuntime.supportsMSync`/`canUpgradeRuntime`, the planner's runtime facts (MSync, Mono TLS) and storage cleanup's current-runtime and managed-name checks use it instead of three hand-written copies of the `wine-<version>-<digest>-winemac-wine11.0-metal.` stem and the hard-coded `1...6`. Membership is now exact: only a plain decimal revision directory holding the managed `wine` executable counts, so a malformed revision or another file under a managed runtime no longer gets the Mono TLS correction; a newer revision from a newer MagicWine still does but is neither current nor upgradable. Verified by new tests (current, historical, newer and malformed revisions, other archive digests, custom Wine, aliases, a linked library and a linked revision directory) and the full suite (301 tests).
- Wait for the bottle lock without blocking a thread: `GraphicsPrefix.withLock` (used by every `BottleStore` transition, including the play-history and favorite updates, launch preparation and dependency placement) no longer loops on a blocking `flock(LOCK_EX)` from actor code. It now shares `AdvisoryFileLock` with `GraphicsOperationLease`: nonblocking attempts with short async sleeps, cancellation while waiting never runs the critical section, and a lock still held after 30 seconds fails as `busy` (another operation in progress) instead of hanging; the critical section stays synchronous on the caller's actor and the lock is released with an explicit `flock(LOCK_UN)` before `close`. While one bottle's lock is awaited, `BottleStore` keeps serving other bottles. A launch now takes the lock once for the Desktop, Rosetta CPU repair and XInput bridge instead of three times. Verified by new tests (a lock held by another process is awaited and then acquired while the store serves another bottle, cancellation while waiting, timeout as `busy`) and the full suite (295 tests).
- Report failures as structured errors with their log and recovery actions instead of text: `MagicWineError` now names the kind of failure (invalid input, not initialized, busy with running programs or another operation, conflict, consent required, timed out, process failed, stopped, operation failed, runtime unavailable/incompatible with a remedy, invalid graphics component, unsupported host, integrity failure, unsafe filesystem refusal, download failure) and exposes `logURL`, `recoveryActions` (show log, stop, retry setup, restore Standard, update component, update Wine, choose Wine, install Rosetta, consent, reload, retry) and a surface-neutral `recoverySuggestion`. Messages no longer embed log paths or CLI/GUI instructions; for example MSync on an older managed runtime offers Update Wine while custom Wine offers choosing another Wine. Wrapped install failures keep the underlying recovery actions. 226 core `.setup` sites became 16 genuinely generic ones (system `strerror`/enumeration failures, one internal launch invariant, a failed recovery after a failed transaction). The CLI prints `error:`, `log: <path>` and a `hint:` command per action that applies to the named bottle (`CommandLineErrorReport`), with unchanged exit codes; the dashboard's failure card (`ErrorPresentation.swift`) shows the guidance, **Show Log** for that failure's log, and buttons for Stop, Retry Setup, Restore Standard Graphics, Update Component…, Update Wine…, New Bottle with Other Wine… and Reload; alerts carry the guidance and log. Verified with new mapping and CLI-rendering tests (288 tests, three consecutive runs), CLI errors under a temp root (bad UUID, graphics on an uninitialized bottle, missing consent, MSync on custom and older managed Wine, missing Wine, runtime upgrade without the updated runtime), and the app starting under a temp `MAGICWINE_DATA_ROOT` (visual check of the card not possible here).
- Track running programs and play history per program. `BottleActivity.running` keys launches by program ID instead of anonymous UUIDs, so each program row shows **Running**, the sidebar and dashboard name the running programs, and launching a running tray launcher again still reopens it (its **Show Running Log** follows the newest launch). Programs persist `lastLaunchedAt` (when the app saw the process start), accumulated `playTime` (from the first start until the program's last overlapping launch ends, measured in system uptime so sleep is not counted) and an `isFavorite` flag, written only by the new metadata-only `BottleStore.recordLaunch`, `addPlayTime` (finite, non-negative sessions) and `setFavorite` transitions under the bottle lock; a program removed while running is not recorded, general `save` and `updateProgram` keep the saved history instead of overwriting it or reporting a conflict, older records decode as never launched, and unset fields are not written. Program rows show the last launch and play time, a star toggles favorites (also in the ⋯ and context menus), and a Name/Recent switch orders the list with favorites first. CLI launches are not recorded. Verified with 4 new tests (legacy decoding and unchanged encoding, negative play time rejected, launches/play time/favorites persisting and accumulating, invalid sessions and removed programs changing nothing, an editor and a stale general save keeping history recorded meanwhile; 287 tests), a release app build, and the app starting under a temp `MAGICWINE_DATA_ROOT` whose fake bottles carry history fields (no screen capture, so the rows were not inspected).
- Use native macOS navigation in the library window: a `NavigationSplitView` with a collapsible `List(selection:)` sidebar (keyboard navigation; bottles plus Gamepads, Downloads and Documentation) replaces the fixed 250 pt button column, `.searchable` filters bottles by their own or their programs' names and the dashboard lists only matching programs, and a toolbar offers Install EXE/MSI, Add Program, Refresh and Stop for the selected bottle. The duplicate sidebar Settings destination is gone (Wine settings stay in the Settings window, ⌘,) and the dashboard's Settings button is now **Bottle Settings**. The Bottle menu acts on the focused window's selected bottle and clicked program through `focusedSceneValue` and is disabled when not applicable: Install EXE/MSI… ⇧⌘I, Add Program… ⇧⌘A, Refresh Programs ⌘R, Launch *program* ⌘↩, Stop Windows Processes ⌘., Show Bottle Logs… ⇧⌘L, Reveal C: Drive ⇧⌘D, Reload Bottles; New Bottle… ⌘N opens that window's sheet. Selection, the New Bottle sheet, Trash confirmation and files opened before loading finished are per-window state instead of shared model state, and app-wide alerts are shown by the key window only, so several windows no longer mirror each other's sheets and alerts. Verified by the test suite (283 tests), a release app build, and the app starting and staying up under a temp `MAGICWINE_DATA_ROOT` with fake bottles (no screen capture, so the UI itself was not inspected).
- Split the app's `AppModel` god object into focused `@Observable` models: `AppModel` is now the composition root (startup, reload, opening installers, bottle creation), with `LibraryModel` (bottles, creation, per-bottle icon revisions), `RuntimeModel` (runtimes, settings, Wine installation), `BottleActivityModel` (per-bottle operations, launches, live logs, Stop, Trash), `BottleSettingsModel` (graphics, Retina, MSync, HUD, compatibility, program options), `StorageCleanupModel`, `DependenciesModel` and `NoticeModel`; the logic moved unchanged.
