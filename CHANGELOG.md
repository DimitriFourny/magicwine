## Unreleased — 2026-10-24

- Reclaim storage from unused Wine runtimes, graphics components and private runtime views: new `StorageCleanup` plans, read-only, what nothing references (bottles' pinned runtimes and component IDs, `settings.json`, and the exact `GraphicsRuntimeView` identities launch would use; current managed Wine and bundled components kept unless included; unreferenced D3DMetal imports flagged as re-import required), plus abandoned `.install-*` staging and lock files of deleted bottles. Removal recomputes the plan under every bottle's exclusive launch/lifetime lease and a wineserver idle probe, refuses while anything runs, and deletes confirmed entries only through no-follow, descriptor-relative removal inside `Runtimes/`, `Components/` and `Bottles/.graphics-locks/`. Exposed as CLI `cleanup [--apply] [--include-current]` and a Storage card on Downloads with a confirmation listing every path. Verified with new tests (referenced vs unreferenced runtimes/components/views, a bottle pinned to a missing runtime, undeterminable view identities, symlink escapes, refusal under leases and a live server, staging, idempotent apply) and a CLI smoke on a temp root with two real bottles (dry run, refusal while a program and then its server ran, apply, kept view still launching).
- Deduplicate the security-critical filesystem, hashing and binary-inspection helpers: new `SecureFS` (no-follow `lstat`/open, bounded streaming SHA-256, stamps plus validation cache, exclusive `renamex_np` publication, quarantine preservation), `MachOInspector`, `PEInspector` and the shared `BundledArchive` copy/hash/member-check/extract stage replace the private copies in the DXVK, DXMT, D3DMetal, graphics-view, Wine Metal driver, Rosetta CPU, XInput bridge, Desktop, Wine-download and graphics-prefix code (net −301 source lines). Size limits, hard-link tolerance and builtin-marker rules stay explicit per caller; pins, receipts, layouts and journals are unchanged. Every bounded hash/read now also rejects a file replaced or modified while read and honors cancellation, and D3DMetal's Mach-O check uses the stricter shared parser. Verified with the unchanged component suites plus new `SecureFSTests` (219 tests) and real managed Wine under a temp root: DXVK → DXMT → Standard → DXVK each followed by a successful `exec cmd /c exit 0`.
- Add GitHub Actions CI (`.github/workflows/ci.yml`): a macOS job runs `./scripts/test.sh`, `./scripts/build-app.sh`, and a packaged-CLI smoke test, and an Ubuntu job runs `shellcheck -x scripts/*.sh`. Checkout never smudges Git LFS objects; `.git/lfs` is cached on a hash of `git lfs ls-files --long` and pulled only on a miss, which is harmless before any LFS migration. Real-Wine runners are intentionally excluded. ShellCheck 0.10.0 (static binary under gitignored `.local/tools/`) found two items in `scripts/*.sh`, both fixed (a `A && B || C` usage check in `test-wine-proxy.sh`, a justified `SC2034` disable for the sourced `SWIFT_OPTIONS`); the workflow parses as YAML but has not run on GitHub.
- Stop the gamepad bridge recipe from overwriting the pinned historical GPL XInput v1 payload with MIT license text: it now builds a new component identity (default `magicwine-xinput-v2`, `magicwine-xinput-v1` refused), writes a component-specific license name into gitignored `.local/gamepad-bridge-output/<component>/`, refuses existing output, and prints hashes plus adoption steps. Verified with `bash -n`, the v1/invalid/existing-output refusals, and a real MinGW build whose staged v2 hashes differ from, and left byte-identical, the checked-in v1 DLLs and GPL license.
- Let Refresh, Add Program, Remove from MagicWine, and Reload Bottles run while Windows programs (for example Steam in the tray) are running, so new games can be picked up without stopping the client. Consolidate the repeated busy checks into `BottleActivity.blocksPrefixMutation`, `blocksLibraryEdit`, and `blocksLaunch`; graphics, MSync, Retina, installers, Wine update, winecfg, and Trash stay blocked while programs run. Library edits only touch bottle metadata under the bottle lock.
- Report each bottle-operation failure once: MSync, Retina, and graphics failures now show only the inline Operation Failed card instead of an alert plus the card. Notices carry an optional log and the alert, migrated off the deprecated `Alert` API, offers Reveal Log (that file) only when one exists, so "Unsupported File" and "Choose a Bottle First" no longer open the log folder.
- Launch programs even when an optional compatibility step fails: an unreadable controller profile, a custom/invalid XInput DLL or damaged bridge backup, or a custom `wow64cpu.dll` now skips only that component. A skipped bridge forces Wine's builtin XInput (`=b`) without the gamepad session variable; a skipped CPU repair adds no `wow64cpu` override. Warnings reach the user as soon as the process starts (dashboard notice with Reveal Log, CLI stderr) and are written at the top of the process log; cancellation and Stop still abort. Verified with fake-Wine launch tests (custom XInput DLL left untouched, builtin overrides and no session variable in the recorded environment) and a real Rosetta refusal of a custom CPU DLL.
- Treat a directly launched program's exit code as data: a game or launcher that quits with a nonzero code no longer shows "Operation Failed", but a dismissible notice "<program> exited with code N" with the last few Wine `err:` lines from a bounded 64 KiB log tail and Reveal Log for that log. Setup, installers, Wine commands, signals, and failed LNK/URL dispatch keep error semantics. CLI `launch` prints and exits with the program's code; `exec` prints the log and exits with Wine's code. Verified with fake-Wine tests (exit 3 returned, wineboot/dispatch/exec failures still thrown), log-summary tests for CRLF, symlinks, huge logs, and partial tail lines, and real managed Wine (`exec cmd /c exit 3` → 3, `exit 300` → 44, `reg.exe` launch → 1).
- Change the graphics HUD without stopping the bottle: the HUD is launch environment only, so the dashboard toggle and CLI `graphics <bottle> <current-backend> --hud|--no-hud` now save just `graphics.showHUD` under the bottle lock for programs launched afterwards, stay available while programs run, and need no re-verification, Stop, or `--accept-experimental`. Standard, unsupported components, stale backend views, and overlapping setting changes are refused. Verified with a fake-Wine test (HUD changes while a program runs, which keeps running, persist to `bottle.json`, and leave the prefix untouched) and real managed Wine on a DXVK bottle (HUD on in 0.06 s while `cmd` kept running and later exited normally).
- Assemble every Wine launch in a pure `LaunchPlanner` with typed `DLLOverrides` instead of concatenating `WINEDLLOVERRIDES` inside `WineRuntime`: fixed layers (managed base < compatibility integrations < graphics backend < bottle < program) where a higher layer wins per variable and per DLL, one deterministic Wine-syntax serialization, and side effects (prefix DLLs, folders, runtime views, leases) still in `WineRuntime`. Variables and load orders are unchanged; a DLL named by two layers now resolves to the higher layer instead of being listed twice, and adjacent DLLs with the same mode may share one segment. Verified with planner tests for the exact environment of Standard, DXVK HUD on/off, DXMT, and D3DMetal, layer precedence, parse/serialize round trips and invalid syntax, the inherited-variable scrub policy, MSync, and Mono TLS, plus real managed Wine `cmd /c set` on Standard, DXVK, and DXMT bottles showing the same `WINEDLLOVERRIDES` strings as before.
- Add per-program launch options: arguments and a working directory for EXE programs, plus environment variables and DLL overrides for every program, edited with **Edit…** in the program's menu (sheet with shell-style arguments and their parsed tokens, folder picker, inline validation) or CLI `program <bottle> <program> [--name] [--args] [--workdir|--clear-workdir] [--env|--unset-env] [--dll|--unset-dll]`.
